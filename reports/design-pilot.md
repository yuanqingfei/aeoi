# 设计任务试点

## 摘要

`gemini-flash-lite-latest` 跑了 7 道 EngDesign 题（`reports/design-gemini_gemini-flash-lite-latest.json`，temperature 0，`--max-steps 10`，`--rpm 10`）：**0/7 通过，5 道提交了答案，有分数的 5 道平均 43.6**。另有一次 `gemini-3.1-flash-lite` 在 XG_13 的第一次请求上收到 HTTP 503，重试后失败（`reports/design-gemini_gemini-3.1-flash-lite.json`，约 130 秒，0 次工具调用）。ControlEval 那次没有留下报告：进程大约一小时没有新的检查点，被杀掉了。

失败主要是模型没有把设计做完或做错了，不是评分器把参考答案判错。10 道 EngDesign 的参考提交在单元测试里都是 100 分。评分器有一处真问题：XG_02 按细则应该给部分分，旧实现只有 100 或 0；修完之后，试点里那份稳定但带宽不对的控制器从 0 分变成 60 分，五道有分数的题平均变为 **55.6**，通过数仍是 0。无穷相位裕度以前被写成 JSON `null`，比较时却已经当作通过，报告看起来像缺了字段。

按“能多解开几道题”排序，缺的是传递函数串联/反馈，然后是 PID 构造，然后是不用手算闭环就能看调节时间和超调的便利函数，再然后是时滞的 Padé。控制器的 `c2d` 和 MIMO 裕度在这 7 道题里用不上。这些算子本次没有实现。

### XG_13（模型推理）

对象是 `1/(s²+10s+20)`，要求 2% 调节时间 < 0.2 s、超调 < 5%、稳态误差为 0。模型用 `step` 和 `poles_zeros` 看过自己拼的闭环，稳定性和调节时间是对的，超调差 1.5 个百分点。它口头说超调是 0，和工具返回不一致。串联/反馈算子会让它直接检查**最终提交的** Kp、Ki、Kd，少一次手算多项式的机会，但这次它已经会调用 `step`，没过是因为最后一组增益本身超调偏大。

### Ziheng_03（模型推理 + 缺 PID / 串联）

对象是 `1/((0.5s+1)(s+1)(2s+1))`，要 5% 调节时间、超调、稳态误差、GM > 10 dB、PM > 45°。模型会手写带积分器的分母（末项 0），然后连续 9 次只看 `margin`，步数用完。`step` 已经能给出调节时间和超调，它没有调用。PID 构造和“对象 × 控制器 → 闭环阶跃”会把这 10 步从手算系数里省出来。

### XG_05（模型推理）

辨识公式在题面和参考解里都有，不需要图，也不需要新算子：τ = 3/2 (t2−t1)，θ = t2−τ。模型没有用这两个数。时滞的 Padé 只影响“拿辨识出的模型去验控制器”；θ、τ 交错了，那 20 分用 Padé 也补不回来。相位裕度是无穷（没有增益穿越），旧报告写成 `pm_deg: null`，分数仍按“大于 60°”给了 20 分。这是报告格式问题，不是这道题没过的原因。

### XG_11（schema + 模型推理 + 缺串联）

对象是 `(0.5/s)·169/(s²+0.26s+169)`。模型第一次 Bode 用了对的数量级，第二次把频率对象多包了一层 `explicit`，第三次 logspace 的 min = max，第四次改对。之后它把对象分母写成 `[1, 0.26, 0, 0]`，共振项 169 没了，再用越来越高阶的多项式去试裕度，10 步用完，没有提交。schema 报错带了 remediation，模型也改了；卡住设计的是手算串联，以及它改错了对象。

### XG_12（模型推理 + 缺串联）

同一类回路成形，带宽改成 3 rad/s，要陷波。模型只 Bode 了对象（分母是对的），然后交了 `C_num ≈ [2.65, 37.4]`、`C_den = [1, 0]`、`ωn = 13`、`αn = 0.1`、`fn = 1`。参考的 Kg·Ki 大约是 `[17.96, 17.04] / [3.32, 0]`，归一化之后也不等价，闭环有正实部极点，0 分。没有调用 `margin` 或 `step`。

### XG_02（schema + 模型放弃 + 评分器）

七阶 SISO 状态空间，要带宽约 85 Hz、GM > 1.5 dB、PM > 60°。`control_lti_convert` 已经能 ss→tf，模型却调用了 `ctrb_obsv`，矩阵用了嵌套数组。schema 诊断落在 oneOf 的“缺少判别字段 order”上，嵌套数组的无损补丁没有出现。模型没有改，下一回合交了 `num=[100]`、`den=[1, 100]`，并写“初步提交测试控制器”。

这份控制器闭环稳定，增益裕度约 14.8 dB，没有 0 dB 穿越（带宽记 0），相位裕度无穷。细则是带宽 40、增益裕度 30、相位裕度 30。旧评分器在三个条件没有同时成立时给 0。按细则应是 60，通过仍为否。上游 `evaluate_controller.m` 把 MATLAB `margin` 的**绝对**增益裕度放进名为 `Gm_db` 的变量再和 1.5 比；题面和细则写的是 1.5 dB，评分按 dB，绝对比较留在 `upstream_literal_pass`。

### LX_02（模型推理；非线性不在算子范围内）

磁悬浮线性化、状态反馈和观测器用 `place` 做对了（A、B、K、L 共 36 分）。s1..s4 是吸引域的是/否，参考为 1,0,1,0，模型给了 1,1,0,0，s1 和 s4 对（32 分里的 32 有一半），合计 68。现有算子都是线性的，做不了这四问的仿真。模型是在猜交替模式，猜错了中间两项。

## 挂起：ControlEval 为什么看起来停了一小时

仓库里没有那次运行的报告，和当时的写法一致：`checkpoint` 只在一道题**结束**之后调用。第一道题只要还停在 `chat` 里，`reports/design-*.json` 就不会出现，终端也只有重试日志。

单次请求的旧上限是：

* HTTP 客户端超时 180 秒；
* 传输错误、408、429、5xx 都重试，最多 6 次；
* 退避取服务端 `retryDelay` 和指数退避的较大者，封顶 65 秒；
* 只有“每天配额”（正文里有 per-day）或 `retryDelay` 大于封顶的 3 倍才立刻放弃。

一次卡住的连接因此可以到大约 `7 × 180 s + (2+4+…+64) s`，二十分钟量级；再乘 `--max-steps 10`，一道题就能超过一小时，而且一个字节的报告都没有。Gemini 的每分钟 429（`retryDelay` 几十秒、不是 per-day）会按这个循环睡下去。503 “high demand” 同样会重试——另一份报告里，XG_13 的第一次调用光是把 503 重试完就用了 130 秒。

现在的行为（`provider.rs` 的 `RetryPolicy`，`design.rs` 的循环）：

* 单次 HTTP 超时默认 90 秒，一次 `chat` 的重试墙钟默认 150 秒，到了就返回错误，不再睡下一轮；
* 每日配额仍然立刻返回 `QUOTA_EXHAUSTED`，设计循环记下当前题并停止，`aborted.not_run` 只含还没开始的题；
* `--call-timeout`（默认 150 秒）包住整个 `chat`，包括内部退避，超时则这道题记 `call_timeout` 并进入下一题；
* `--task-timeout`（默认 600 秒）包住一整道题；
* `--max-steps` 仍是模型回合数的硬上限（空回合的提醒也算一步）；
* 报告在题目开始时写成 `stopped: running`，每个回合后再写一次；写入是“临时文件 + 改名”，杀掉进程不会把上一份检查点写坏。

离线覆盖：`mock:design`、`mock:script`，以及单元测试里的最大步数、提交后打分、调用超时、题目超时、日配额不睡眠、短暂 429 按 `retryDelay` 重试后成功、挂起的套接字被超时和预算截断。这些测试不访问外网。

按上面的排序实现了前四项，没有做 pidtune。规范因此改了五处（3.12、F-7、I-10、A-1；见 spec changelog）：返回的 `result.system` 可以原样再送进去，收据不嵌套；阈值和 `sign = -1` 是定义默认值，Padé 的 delay 和 order 必填但不必从原话里摘引文；stepinfo 的时间是网格定义；Padé 的逼近误差单独放在 `approximation`，没有严格上界时 `bound` 是 null。

## 缺的能力，按能解开的题排序

下面是试点当时的排序，原样留下。前四项已在 v0.3.5 做成算子，见上一节；这里不再改原文。

只建议，不在这次实现。排序看这 7 道题加上 ControlEval 的题型（连续、单位负反馈、有的带时滞），不看还没跑的离散设计。

1. **传递函数串联、反馈、并联。** 7 道里有 6 道要自己乘多项式、自己加闭环分母（LX_02 除外）。ControlEval 每一题都是 L = G·C、T = L/(1+L)。XG_13 已经能手算，但交上去的增益和它仿真的多项式不是同一个；Ziheng_03 和 XG_11 把步数耗在手算上。这是影响面最大的一块。
2. **`pid` / `pidtune`。** XG_13、Ziheng_03 的答案就是 Kp、Ki、Kd。Ziheng 的 10 步全是在试系数。ControlEval 的提交格式也是控制器分子分母，一个能按裕度和调节时间给出初值的 `pidtune` 会直接改变能不能在 `max_steps` 里交卷。
3. **闭环阶跃指标（plant + controller → stepinfo）。** `control.lti.step` 已经返回调节时间、超调和稳态值，缺的是不用先拼出 T(s)。Ziheng_03 和 XG_05 一次 `step` 都没有；XG_13 拼对过一次，但没有拿最终增益再跑。
4. **时滞 / Padé。** XG_05 的控制器验算和 ControlEval 里 `tau > 0` 的题需要它。XG_05 的 θ、τ 本身用题面的 t1、t2 就能算，Padé 解不开这道题的辨识分。
5. **带宽读数，以及提醒模型用已有的 ss→tf。** 只有 XG_02。`control_lti_convert` 已经能把状态空间转成传递函数，模型选了 `ctrb_obsv`。单独的带宽算子帮助有限，除非它接受“对象 ss × 控制器 tf”。
6. **控制器的 `c2d`。** 这 7 道都是连续的。AV_02 / AV_03 直接交离散系数，用现有的离散 Bode 就能评分。ControlEval 也是连续的。对还没进这批评测的离散控制器设计会有用，对这次试点没有。
7. **MIMO 裕度。** `control.analysis.margin` 只做 SISO，规范里写了。EngDesign 这 10 道和 ControlEval 的厂模型都是 SISO（XG_02 是七阶，但是单入单出）。这次没有题被 MIMO 裕度挡住。
8. **非线性吸引域。** 只有 LX_02 的 s1..s4（32 分）。不是线性时不变算子能覆盖的，不建议为了这一题加仿真器。

schema 上的摩擦，同样不在这次改：Bode 的 `frequency` 是 oneOf，模型会多包一层；logspace 要求 min < max，报错是清楚的，模型也改了；`ctrb_obsv` 在矩阵写成嵌套数组时，诊断停在“缺 order”，F-4 的嵌套数组补丁没有出来。XG_02 因此浪费了唯一一次工具调用。

## 评分器

对照了上游 EngDesign `c8ec338` 的 `tasks/XG_13/evaluate.py`、`tasks/XG_02/evaluate_controller.m`、`tasks/AV_03/evaluate.py`，以及仓库里的 `scoring_notes`。

* 10 道参考提交仍然满分。XG_13 的上游检查是 Ts < 2 s 且 Overshoot < 0.05；python-control 的超调是百分数，所以上游等于要求超调 < 0.05%。我们按题面（< 0.2 s、< 5%）判通过，`upstream_literal_pass` 保留上游那条。这是原有的、写在 README 里的偏差，不是这次试点判错的原因。试点的 XG_13 两种标准都不过（0.147 s 但超调 6.45%）。
* **修了 XG_02。** 细则和上游 MATLAB 都是部分分：带宽 40、增益裕度 30、相位裕度 30，不稳定为 0。旧代码在三者没有同时成立时给 0 或 100。试点那份 `100/(s+100)` 因此从 0 改为 60（增益裕度和相位裕度成立，带宽不成立），通过仍为否。增益裕度继续用 dB，和题面一致；和 MATLAB 绝对裕度的比较留在 `upstream_literal_pass`。
* **修了非有限数的写法。** `json!(±Inf)` / `json!(NaN)` 会变成 `null`。XG_05 和 XG_02 的相位裕度是无穷，旧报告是 `pm_deg: null`，`pm > 60` 却为真。现在写成 `"Inf"` / `"-Inf"` / `"NaN"`（和算子信封的 R-2 一样）。XG_05 的分数不变，仍是 80。
* 其余题的通过条件和部分分（PID、回路成形、磁悬浮、IIR/FIR 权重、α 区间）和修正前一致。`pyscore.py` 仍只比较通过/不通过，不比较百分制。
